# Training Reference

Every training run resolves a method + hardware preset via the merge chain
`configs/base.toml → configs/presets.toml[<preset>] → configs/methods/<method>.toml → CLI args`
(method beats preset on overlap; CLI args still win last).
Method TOMLs in `configs/methods/` are toggle-block files that hold several
variants behind comments; the clean per-variant tree lives in
`configs/gui-methods/` and is selected with `python tasks.py lora-gui <variant>`.
The `make` targets remain available as compatibility forwarding wrappers.

```bash
python tasks.py lora                           # methods/lora.toml + presets[default]
python tasks.py lora PRESET=low_vram           # any preset can be swapped in
python tasks.py lora-gui tlora                 # one self-contained variant file
python tasks.py print-config METHOD=lora PRESET=default  # dump the merged config
```

Run `rg --files configs/gui-methods` for the live variant list.

## LoRA family — the three-axis surface

`configs/methods/lora.toml` covers LoRA / OrthoLoRA / T-LoRA / HydraLoRA / FeRA /
ReFT under one routing surface:

```toml
use_moe_style    = false | "shared_A" | "independent_A"
route_per_layer  = true | false
router_source    = "none" | "input" | "sigma" | "fei"
                 | "crossattn_emb"
```

The shipped `configs/methods/lora.toml` default is not plain LoRA: it enables
OrthoLoRA + T-LoRA on a Hydra shared-A stack with `router_source = "input"`.
For a plain baseline, use `configs/gui-methods/lora.toml` via `lora-gui`.
FEI-on-Hydra and author-faithful FeRA remain manual three-axis experiments; no
FeRA GUI preset TOML is shipped right now.

Pre-three-axis checkpoints carrying `ss_use_hydra` / `ss_use_fei_router`
metadata no longer load — the legacy fallback was removed.

### OrthoLoRA (Cayley + PSOFT-inspired)

Cayley-parameterized orthogonal rotation of frozen SVD bases with a zero-init
guarantee. Orthogonality is structural — no regularization knob.

```toml
use_ortho = true
```

Linear layers only (no Conv2d). See [`../methods/psoft-integrated-ortholora.md`](../methods/psoft-integrated-ortholora.md).

### T-LoRA (timestep-dependent rank masking)

Early (high-noise) steps use full rank; later steps use reduced rank.
Composes with every variant in the family. Training-time only — inference
runs full rank by design.

```toml
use_timestep_mask = true
min_rank = 8
alpha_rank_scale = 1.0
```

Schedule: `r(t) = floor((1 - t)^alpha_rank_scale * (network_dim - min_rank)) + min_rank`.
See [`../methods/timestep_mask.md`](../methods/timestep_mask.md).

### HydraLoRA / FeRA / Hydra+FEI

Multi-head expert routing variants. See [`../methods/hydra-lora.md`](../methods/hydra-lora.md)
and [`../../docs/experimental/fera.md`](../experimental/fera.md). The
`balance_loss_weight` ceiling is ~5e-5 on Anima — above that the Switch loss
saturates.

### ReFT

Block-level residual-stream intervention. Off by default; flip
`add_reft = true` and pick a layer band (`reft_layers = "last_8"`).
See [`../methods/reft.md`](../methods/reft.md).

### Postfix

Postfix training/config entries are historical and are not registered in the

- `python tasks.py exp-invert-directedit`

## FP32 accumulation

Unconditional. LoRA / Hydra / ReFT bottleneck matmuls run in fp32 regardless
of autocast; stored parameters stay bf16. The legacy `lora_fp32_accumulation`
flag is deprecated and ignored.

## Cross-attention KV trim

Removed — the trim path only ran under `attn_mode = "flash4"`, which we
evaluated and dropped. See [`../optimizations/fa4.md`](../optimizations/fa4.md).
Training now always runs full 512-length cross-attention KV; the zero-padded
positions act as attention sinks and cost negligible compute on FA2.

## Caption shuffle variants

Pre-cached caption permutations, one drawn per batch item per epoch — extra
diversity without re-running the text encoder.

```toml
caption_shuffle_variants = 4         # generated by preprocess-te
use_shuffled_caption_variants = true # picked at train time
cache_text_encoder_outputs = true
```

The shuffle preserves `@artist` tags and section markers (`On the ...`,
`In the ...`); only intra-section tags rotate. Regenerate the cache after
changing tokenizer or padding.

Anima and Krea-2 both support this cache layout. Krea-2 stores Qwen3-VL
`hiddens`/`mask` variants in `{stem}_krea2_te.safetensors`; changes to caption
source mode, caption extension, variant count, or tag-drop rate invalidate the
preprocess cache. `caption_dropout_rate` remains a training-time policy and does
not require regenerating text embeddings.

## Masked loss (SAM / MIT)

Exclude regions like text bubbles from the training loss. `masked_loss = true` is on by
default in `base.toml`. 注意：只把它设为 `false` 并不能覆盖 batch 已经携带的
`alpha_masks`；当前 loss 路径在任一 alpha mask 存在时仍会应用 mask。要做真正的
整图训练，数据集行还必须不提供 mask（若全局 mask 目录存在，显式设
`mask_dir = ""` 以阻止自动探测）。

```bash
python tasks.py mask        # SAM3 + MIT (via tempdir) → post_image_dataset/masks/
python tasks.py mask-clean  # rm -rf post_image_dataset/masks/
```

These read `post_image_dataset/resized/` (the resized output of
`python tasks.py preprocess`). Subsets auto-pick `post_image_dataset/masks/` if
present, falling back to legacy `masks/{merged,sam,mit}/` so users who
haven't re-run `python tasks.py mask` after the consolidation keep training.

## Dataset configuration

The default LoRA blueprint lives in `base.toml` (under `[general]` /
`[[datasets]]` / `[[datasets.subsets]]`) and is *not* part of the flat
merge chain — `_DATASET_CONFIG_SECTIONS` in `library/train_util.py` skips it
so it never pollutes argparse. Top-level path keys interpolate into the
blueprint at load time:

```toml
source_image_dir  = "image_dataset"            # captions live here
resized_image_dir = "post_image_dataset/resized"
lora_cache_dir    = "post_image_dataset/lora"

[general]
caption_extension = '.txt'
keep_tokens = 3

[[datasets]]
resolution = 1024
batch_size = 1
enable_bucket = true
validation_split_num = 0
validation_seed = 42

  [[datasets.subsets]]
  image_dir = '{resized_image_dir}'
  cache_dir = '{lora_cache_dir}'
  num_repeats = 1
```

`cache_dir` redirects every VAE / TE / PE sidecar to a flat,
stem-keyed location — used so IP-Adapter and EasyControl can keep their
source dirs (`ip-adapter-dataset/`, `easycontrol-dataset/`) purely
user-facing while caches all land under `post_image_dataset/`.

To shallow-override the blueprint, drop a `[general]` / `[[datasets]]` block
into the method TOML — `_apply_dataset_overrides` in `library/config/io.py`
merges top-level scalars (e.g. `batch_size`). Subset-level keys must go
through `--dataset_config <path>`.

The `[half]` preset (and similar) sets `sample_ratio = 0.5` for every
subset via the global `--sample_ratio` override — it shrinks **train only**;
validation count stays exact.

## Validation

Validation is **disabled by default** in `configs/base.toml`
(`validation_split_num = 0`, no positive `validation_split`), and the shipped
GUI variants explicitly set `use_cmmd = false`. The default `methods/lora.toml`
method overrides the held-out count to `8`, but still inherits
`use_cmmd = false`, so that CLI path uses the legacy per-σ FM-MSE validation.

To enable paired CMMD² (PE-Core MMD between paired samples), set
`use_cmmd = true` and configure either `validation_split_num` (integer count)
or `validation_split` (fraction). CMMD adds sampling and PE-encoder cost; with
CMMD disabled, a positive validation split uses FM-MSE instead.

## Multi-GPU

The standard `train.py` path supports data-parallel adapter training through
an Accelerate launch. In the WebUI, selecting two or more GPUs automatically
starts one worker per selected GPU. The "all GPUs" choice is expanded to the
GPU indices returned by the WebUI GPU inventory, so it follows the same rule.
Preprocessing remains single-process; its selected GPU list is carried into
the training launch.

For CLI launches, opt in explicitly with both variables:

```bash
ANIMA_ACCELERATE_LAUNCH=1 \
ANIMA_ACCELERATE_NUM_PROCESSES=2 \
.venv/bin/python tasks.py web --host 127.0.0.1 --port 20102
```

The adapter network is registered with Accelerate for device placement and
checkpoint state, but deliberately is not DDP-wrapped. Adapter forwards run
through monkey-patched frozen DiT/text-encoder modules rather than through the
network container's root `forward`, so a normal DDP wrapper has the wrong
forward boundary. `library/training/gradient_sync.py` instead:

- broadcasts optimizer parameters and network buffers from rank zero once;
- mean-reduces adapter gradients in fixed buckets once per `sync_gradients`
  step; CUDA/NCCL buckets launch from backward hooks on a communication stream
  and overlap the remaining backward work;
- contributes zeros for a rank-local `grad=None`, while preserving `None` when
  a parameter is unused on every rank;
- synchronizes before router statistics, finite checks, and gradient clipping.

Methods that inject additional gradients from `after_backward` intentionally
use the synchronous fallback so those contributions are included exactly once.

Gradients remain loss-scaled during the collective. This propagates FP16
overflow to every rank before GradScaler unscales/checks the gradients, keeping
the optimizer skip decision consistent. The effective global batch is
`train_batch_size * num_processes * gradient_accumulation_steps`; retune LR or
accumulation when changing the process count.

This support applies to commands that use the standard `train.py` launcher.
Bespoke experimental loops that bypass it remain single-GPU unless their own
documentation says otherwise.

### Multi-GPU startup admission

The card selection and the worker count must agree **exactly**. When a GPU
selection is present and the launch is active, `num_processes` must equal
`len(selection)`; fewer workers than cards *and* more workers than cards are both
refused, with stable reason codes:

| Situation | Reason code |
| --- | --- |
| one worker over several selected cards | `multigpu_single_gpu_multi_process` |
| any other count mismatch (fewer or more workers than cards) | `multigpu_num_processes_selection_mismatch` |
| launch requested but the resolved count is 1 | `multigpu_launch_without_workers` |
| launch disabled (`ANIMA_ACCELERATE_LAUNCH=0`) | worker count is dormant, not rewritten |

Writing an explicit worker count is **not** an escape hatch: there is no approved
multi-worker-per-card mode, so a conflicting explicit value is rejected instead of
being "preserved". The CLI, the daemon and the WebUI launcher raise the same code
because they all go through `library/runtime/launch.py` and
`library/training/multigpu/admission.py`. Single-process launches keep their
previous behaviour exactly: no collective is issued and no extra file is written.

### Startup probe

`--multigpu_startup_probe` (or `ANIMA_MULTIGPU_STARTUP_PROBE=1`) is **off by
default**. When enabled on a multi-process run it issues one small collective
before training: every rank reduces a vector of ones and checks that the result
equals the world size. Use it when you suspect ranks disagree about topology
(wrong `WORLD_SIZE`, a worker that failed to join, a mixed preprocess/training
environment).

Failure behaviour is fail-closed and symmetric: the probe result is agreed across
ranks and **every** rank aborts with the same named error, so the job never
continues with a partially joined group. On a single process the flag is a no-op.

### Runtime identity manifest

A multi-process run writes `<output_dir>/multigpu_identity.json` from rank 0,
covering **every** rank (one small `all_gather` of device/precision/world size).
It records:

- `world_size` (how many workers really joined) and `configured_world_size` (what
  the launcher intended) as **separate** fields;
- the per-rank device/type/index mapping and the effective mixed precision with
  its source;
- `reduction_mode`, `gradient_buckets` and `reduced_parameter_count`, filled from
  the real `synchronize_optimizer_gradients` result at the first optimizer
  boundary (`pending_first_boundary` / `null` before that, never a guess).

In a multi-process run a manifest that cannot be written is a **named failure**
(`multigpu_identity_write_failed`) agreed across ranks: a run without identity
evidence is not started rather than continued. `--output_dir` is therefore
required for multi-process runs.

### Precision on V100

The launch path never assumes native BF16. On `sm_70`-class cards (V100) the
precision policy rewrites `bf16` to the actual `fp16` path and records the rewrite
source in the identity manifest (`mixed_precision.source`), so a run cannot report
a precision it is not using. FP16 keeps gradients loss-scaled until the
synchronized finite check, which is what makes the skip decision identical on all
ranks.

### State saves are all-rank, publishes are rank-0 only

Every resumable save — step cadence (`save_every_n_steps`), epoch cadence
(`save_every_n_epochs`), `checkpointing_epochs` and the end-of-training save —
goes through `checkpoints.publish_state_with_bundle`. Each rank writes its own
shard, RNG state, `rank<N>.json` cursor artifact and then reports to the group;
rank 0 alone renames the directory. Two consequences that are easy to get wrong:

- The cadence calls must be made by **every** rank. A rank-0-only call leaves the
  other workers outside the first collective of the publish protocol, which is a
  barrier — the save then blocks until the process-group timeout instead of
  failing. The model file itself (`*.safetensors`) is still written by rank 0.
- The save enters exactly **two** agreements in a fixed order: the *capture*
  verdict right after each rank's own `accelerator.save_state` (before the
  pre-publish barrier), then the *publish* verdict after rank 0 renamed the
  directory. Negotiating a capture failure from the `except` block pairs a failing
  rank's collective against its sibling's barrier — the same hang from the other
  side. A transport-looking failure starts **no** collective and does not delete
  the shared `*.tmp` directory: a peer may still be writing into it.

A step-cadence state has no epoch in its directory name, but the position it
records is `(step, epoch, cursor)`: the epoch comes from the loader cursor, so a
step save does not refuse its own per-rank cursors.

### Resume bundle: what counts as exact

`multigpu_resume_bundle.json` is written by rank 0 into the published state. A
resume is **exact** only when all of the following hold, and each failure has its
own code:

| Condition | Code | Result |
| --- | --- | --- |
| no bundle at all | `multigpu_resume_legacy_not_exact` | allowed, not exact |
| version mismatch / unreadable | `multigpu_resume_bundle_invalid` | refused |
| `rank_devices` missing a rank, or naming one this `world_size` does not have | `multigpu_resume_bundle_invalid` | refused |
| different `world_size` (or backend) | `multigpu_resume_topology_mismatch` (`..._degraded` with the explicit opt-in) | refused / degraded |
| RNG streams not proven from `random_states_*.pkl` | `multigpu_resume_topology_degraded` | not exact |
| cursor has no integer position | `multigpu_resume_cursor_unknown` | not exact |
| cursor != what this resume will skip to | `multigpu_resume_cursor_mismatch` | not exact |
| `random_states_*.pkl` no longer readable **at resume time** | `multigpu_resume_rng_evidence_missing` | not exact |
| readable, but a stream is gone or contradicts the bundle **at resume time** | `multigpu_resume_rng_streams_degraded` | not exact |

An incomplete `rank_devices` is **invalid**, not degraded: the publish path builds
that mapping from every rank's own report, so a partial mapping proves the state
was not written by a save of this size. "Degraded" is reserved for a *known*
topology change. The comparison of the cursor happens in
`train_session.verify_resume_cursor`, through
`resume_protocol.guard_resume(..., rank=<this rank>, resume_cursor=<expected>)`, so
each rank compares its *own* saved position with the position it is about to skip
to; extra fields in the cursor artifact (device type/index, batches per epoch) are
recorded but never counted as drift.

### Per-sample noise/timestep fixture (measurement only)

The single-vs-dual numeric gate needs the same `(noise, timestep)` for the same
sample in every run. `library/training/multigpu/noise_fixture.py` provides an
opt-in JSONL fixture (`ANIMA_MULTIGPU_NOISE_FIXTURE=<path>`, one
`{"sample_id", "noise", "timestep"}` record per sample). It is off unless the env
var is set, and a missing/duplicate/wrong-shaped record is a named error rather
than a quiet fallback to a random draw.

Sample ids come from one of two sources (`ANIMA_MULTIGPU_NOISE_FIXTURE_IDS`):

- `batch` (default) — the ids the training batch carries. The Anima dataloader
  emits `image_keys` (the bucket's image keys for the samples of the batch), but
  **only** in the `--debug_dataset` inspection mode, which does not train. A real
  training batch therefore carries no per-sample id and this mode fails closed.
- `cursor` — ids derived from the committed sampler position
  (`s<global sample index>`), which is what `bench/multigpu_reference/hot_run.py`
  selects for the bounded runs. With workers pinned to 0 and a fixed seed, global
  batch `b` is rank `b % world_size`'s local batch `b // world_size`, so the same
  global slot gets the same pinned draw in a 1-worker and a 2-worker run.

Nothing here changes default training behaviour, the loss math, or any admission
decision.

### Per-sample comparison across world sizes (validation only)

The single-vs-dual gate compares the *same sample* in the *same slot*, so the two
runs must shuffle identically. accelerate 1.13.0 does not do that by default: its
multi-process branch re-seeds the sampler from the global RNG and shuffles again,
while the single-process branch shuffles once, so the permutations differ even
with the same `--seed`.

The fix is an **explicit opt-in**, exactly like the noise fixture:

| Switch | Default | Effect when on |
| --- | --- | --- |
| `--multigpu_seedable_sampler` / `ANIMA_MULTIGPU_SEEDABLE_SAMPLER=1` | **off** | passes `DataLoaderConfiguration(use_seedable_sampler=True, data_seed=<--seed>)`, so a 1-worker and a 2-worker run produce the same permutation |
| `ANIMA_MULTIGPU_SEEDABLE_SAMPLER_SEED` | `--seed` | explicit sampler seed |

Off, nothing is passed to `Accelerator` and the loader keeps today's behaviour bit
for bit; on, the sample order of **that** run changes, so every number it is
compared against must have been produced with the same switch (`hot_run.py` pins
the flag in RUN-A/B/C). It affects the sample order only — not the loss math, not
any admission decision, and it is not a production default.

### Per-device batch size

`bootstrap` builds its `DataLoader` with `batch_size=1` because one *dataset item*
already is one batch (`BaseDataset.__getitem__` walks `bucket_batch_size`
samples). The number that matters — samples per device — is the dataset blueprint's
`batch_size`, reachable from config (`--train_batch_size` / `datasets[].batch_size`,
default `1`). `library/training/dataloader_batch.py::resolve_loader_batch` states
both numbers explicitly and fails closed (`dataset_batch_size_mismatch`) when the
configured value disagrees with what the datasets produce, or when subsets disagree
— the step and scheduler arithmetic is computed from the configured value, so a
silent disagreement would train a different batch than the run reports.

With that, "one GPU at `batch_size=2`" and "two GPUs at `batch_size=1`" cover the
same per-update sample multiset: `(local*world + rank)*batch_size + row` gives
`{2k, 2k+1}` for both.

### Resume cursor, RNG evidence and the noise slot

* **Position.** `sampler_position` is the number of local dataloader batches this
  rank has consumed, i.e. the index of the next batch. A resume skips
  `skip_first_batches(initial_step - 1)` **plus** the batch the loop consumes
  through `if state.initial_step > 0: ... continue`, so the counter starts at
  `initial_step` (`cursor.resume_skipped_batches`, the single producer used by
  `train_session` and `expected_position`). The first batch that really runs then
  carries exactly that index; anything treating the counter as a dataloader
  position (the noise fixture) would otherwise be off by one batch after a resume.
* **RNG evidence** is read from the pickles accelerate *really* writes
  (`random_state`, `numpy_random_seed`, `torch_manual_seed`,
  `torch_cuda_manual_seed`), not from the bundle's vocabulary. A state whose
  pickles were written in the older in-tree vocabulary still reports its named
  verdict (`schema: legacy`), but exactness never depends on the schema guess.
* **Second observation at resume time.** The bundle records what the RNG files
  looked like when the state was *written*; that cannot prove the streams will be
  loaded, because accelerate wraps its whole RNG restore in
  `except Exception: logger.info("Could not load random states")`
  (`checkpointing.py`), so a deleted or corrupt `random_states_<rank>.pkl` is
  swallowed and the run silently continues on an unrelated RNG stream. Therefore
  `guard_resume` re-reads the files on the real directory it is about to accept
  (`rng_evidence.observe_state_dir`, the same reader and the same accelerate-key
  schema the save-time check uses) and reports
  `multigpu_resume_rng_evidence_missing` / `multigpu_resume_rng_streams_degraded`.
  It is a few local pickle reads: no collective, no bulk IO, and it does not depend
  on anything accelerate chooses to log or suppress.
* **Order of checks.** The cursor comparison runs *before* the generic RNG verdict.
  A drifted cursor is the specific "the data order moved" failure; leaving it
  behind an early `..._degraded` return made a resume that would replay the wrong
  samples look merely degraded. When both problems exist the RNG one is still
  named in the message.

  Independence is explicit in the result: `ResumeDecision.codes` carries **every**
  named problem that was found (save-time RNG, resume-time RNG, cursor) and
  `ResumeDecision.code` is only the most actionable one. A resume with both a
  drifted cursor and a vanished RNG pickle therefore reports
  `multigpu_resume_cursor_mismatch` *and*
  `multigpu_resume_rng_evidence_missing`, with both explanations in `message`.

### Per-rank digest at the commit boundary (group R)

A state directory cannot answer "do both ranks hold the same thing?": it carries
rank 0's `model.safetensors`, one `scaler.pt`, and one optimizer shard per rank — a
verifier would have to load every shard to compare. So every rank additionally
writes a small digest of what it really holds when the commit boundary is saved:

| file | owner | contents |
| --- | --- | --- |
| `multigpu_rankdigest_rank<r>.json` | rank `<r>` | `adapter` (per-tensor `sha256` over dtype + shape + raw bytes, plus an aggregate over the name-sorted hashes), `scaler` (`present`/`scale`/`growth_tracker`), `optimizer.step`, `scheduler.lrs`, `global_step`, `epoch`, `window` (attempts/replays/discards/consecutive discards + `batches_consumed`/`batches_per_epoch`/`resume_skipped_batches`) |

The comparison is reported as **four axes** — `adapter_equal`, `scaler_equal`,
`optimizer_equal`, `window_equal` (plus `position_equal` for `global_step`/`epoch`) —
so a report can say *which* face of group R failed. Window fields are split:
`window_attempts` / `window_replays` / `window_discards` /
`window_consecutive_discards` / `batches_consumed` are protocol counters and are
compared; `window_total_loss`, `window_last_loss`, `window_num_steps` and
`ema_observation` are **rank-local expectations** (each rank sums its own
micro-batches) and are recorded for observation only — comparing them would raise a
mismatch code that means nothing.

`scaler` reads the counter from `_growth_tracker` (then the legacy public
`growth_tracker`, then `state_dict()["growth_tracker"]`): current torch keeps it in
the private attribute, so a digest built from the old key reported `None` for a
scaler that had clearly stepped. `rank_digest.scaler_state()` also accepts a
**loaded `scaler.pt` mapping**, so R-b can be judged offline from a state directory
that already exists (`{"scale": 65536.0, ..., "_growth_tracker": 10}` after 10
committed fp16 steps).

Rank 0 reads them after the publish and summarizes them into the resume bundle as
`extra.rank_digests` (`schema`, `complete`, `equal`, `codes`, `missing`,
`differences`, per-rank scalars — the per-tensor map stays in the rank file).
`rank_digest.compare()` is the third-party entry point: it returns
`equal` plus the named codes `multigpu_rank_digest_missing` (a rank's file is
absent/unreadable) and `multigpu_rank_digest_mismatch` (a field disagrees, with the
offending field and both values).

Properties this is built on:

* **Observation, not training math.** No collective (each rank hashes its own
  tensors; the comparison is a rank-0 read of files that already landed), and it
  runs only at the commit boundary — never on the per-step path. Measured on CPU:
  ~240 adapter tensors / 2 MB ≈ 7 ms; the cost is pure `sha256`, ≈3.4 ms per MB,
  i.e. a 64 MB adapter ≈ 210 ms per rank **per save**. It scales with the adapter
  size, not with the number of steps, which is why it belongs at the boundary.
* **A difference is a WARNING, not a failure.** A run keeps its verdict;
  `extra.rank_digests.equal` is what a verifier reads. Only a *missing* file and a
  disagreeing field are reported, and both are named.
* **Switch:** on by default, disable with `ANIMA_MULTIGPU_RANK_DIGEST=0` (also
  `false`/`no`/`off`). When off, no digest file is written and nothing is compared.

### Resume verdict in the run identity manifest

A resume also records its own verdict, so a verification ledger can machine-check
"this run resumed exactly" without replaying it: `library/training/multigpu/identity.record_resume_outcome()`
merges three top-level fields into the run's existing `multigpu_identity.json`
(rank 0 only, atomic write, **no collective** — every rank already holds the same
verdict):

| field | meaning |
| --- | --- |
| `resume_exact` | the `guard_resume` verdict for this resume |
| `resume_codes` | every named code that was reported (`multigpu_resume_cursor_mismatch`, `multigpu_resume_rng_evidence_missing`, ...) |
| `resume_bundle_version` | the bundle schema version the verdict is based on |
| `resume.rng_recheck` | `rng_reread_at_resume`, or `save_time_evidence_only` when the caller passed `verify_rng_files=False` |

`ResumeDecision.rng_recheck` makes that distinction visible in the message too: an
`exact` decision that did **not** re-read the pickles says so instead of borrowing
the stronger "re-read at resume time" phrasing.

### Where the validation evidence lives

Per-round verification evidence (ledgers, harness outputs, comparison JSONs) lives
under `output/tests/multigpu_reference_validation/<round>-<date>/` — it is run data,
not source, and this guideline only points at it. The cross-round capability ledger
is `t6-faultinj-cuda-20261108/capability_ledger.md`; the `t3-…` edition of that
ledger is a **historical snapshot** of its round, not the current state of any
item.

The integrated, human-readable reading of all of it — per-reference-point source
location, observation level, command plus exit code and the resulting verdict — is
[多卡参考点集成验收](../findings/multigpu_reference_validation_20261107.md). Read it
before quoting any number from this section: it also records what is **not**
verified (the bounded real runs it reports did **not** pass the single-vs-dual and
10+10-resume numeric gates on V100 fp16, and a skip or a CPU/Gloo pass is never a
CUDA or real-training result).

### Sharding experiment entry

`bench/multigpu_reference/sharding.py::run_two_rank` runs a task in real processes
and refuses a `nccl` backend unless `MULTIGPU_REFERENCE_HARDWARE=1`, before any
spawn (no GPU is touched). `fsdp2_numeric` runs on the device the backend implies,
so it is executable on CPU/Gloo as an integration test and on CUDA under the gate;
its numeric comparison materializes `DTensor` values (`full_tensor`/`to_local`)
because `torch.allclose` refuses a mixed `Tensor`/`DTensor` pair on torch 2.10.
Hardware-marked tests that need an externally provided process group still **skip**;
a skip is not a pass and must not be reported as evidence.

### Verified and unverified scope

- **Verified on CPU/Gloo**: window/`GradScaler` cross-rank agreement, the startup
  admission matrix, checkpoint publish agreement (rank-0 atomic publish, rollback
  when a peer fails, class-II transport exit) and versioned resume bundle
  validation (topology/RNG/loader cursor, legacy = not exact).
- **Verified on small-model CUDA** (`MULTIGPU_REFERENCE_HARDWARE=1`): the real NCCL
  reduction path, the fp16 overflow branch of the scaler agreement (both ranks drop
  and back off together), and the FSDP2/TP toy comparisons.
- **Bounded real Anima runs were executed** (single-GPU batch-2 ×10, dual-GPU ×20,
  dual-GPU 10+10 resume = at most 50 updates, plus a 20-update determinism
  experiment): entry, save, resume and the step budget are established, but the
  single-vs-dual and 10+10-resume numeric gates were **exceeded**, and repeated runs
  with one frozen configuration are not bit-identical on V100 fp16. Treat the
  equality of single- and dual-GPU training as **unproven**, not as passed.
- **Still unverified** (a `skip` here counts as *not executed*, never as a pass):
  cross-bucket / 4032-family / tail-window behaviour (the real run covered one
  896×1200 bucket of the 4200 family), per-rank `GradScaler` growth-tracker
  evidence on real hardware, the fp32 reference path, and FSDP2 / tensor-parallel
  **adoption** (both remain `experimental` and unusable).
- This section documents behavior; it does not approve any deployment, packaging
  or cache/preprocessing side effect. Repository-wide rules stay in `AGENTS.md`.

### Pinned data order for cross-world-size comparisons (`ANIMA_MULTIGPU_PINNED_ORDER`)

Three facts, in the order they bite:

1. **The product default is shuffled, and the shuffle depends on the batch layout.**
   `DatasetBuckets.create_buckets` builds one batch descriptor per batch and
   `shuffle_buckets()` runs `random.seed(seed + epoch)` + `random.shuffle(buckets_indices)`;
   the training loader then shuffles the item stream as well. The descriptor list length
   *is* the batch count (24 images → 12 at `batch_size=2`, 24 at `batch_size=1`), so two
   layouts consume unrelated permutations. Different world sizes therefore see different
   sample orders **by design** — each layout trains legally and this is not a defect.
   Turning the loader shuffle off is *not* enough: the descriptor shuffle is a second,
   independent permutation.
2. **Step-wise equivalence across world sizes only holds under the pinned gate.** With
   `ANIMA_MULTIGPU_PINNED_ORDER=1` the descriptors are sorted into natural order and the
   item stream is served by an identity sampler, so `world=1, batch=2` item `k` and
   `world=2, batch=1` items `2k`/`2k+1` hold the same samples, and accelerate's
   `BatchSamplerShard` hands rank `r` the item `k*W + r`. Only then do slot-by-slot
   comparisons (noise/σ, per-sample loss, Δθ) compare the same data. Do not state
   "multi-GPU equals single-GPU" without this qualifier.
3. **Covered paths.** All three loader construction sites read the same gate through
   `library/training/adaptive_runtime/pinned_order.py`, so they cannot drift apart:
   - the primary train loader (`library/training/bootstrap.py`);
   - the loader rebuilt on a stage switch (`library/training/loop.py`), so
     `stage_schedule` runs are comparable;
   - the stateful recovery cursor loader
     (`library/training/adaptive_runtime/resume_data.py::make_cursor_dataloader`), so
     `adaptive_oom_retry_resume` runs are comparable; it also re-pins the descriptors after
     every epoch advance.

   The epoch boundary is covered too, because it is not a corner case: on 2 GPUs with 24
   samples an epoch is **12 updates**, so a 20-update segment (or the resumed half of a
   10+10 resume, steps 13-20) already runs in epoch 1. The re-pin lives **inside
   `DatasetBuckets.shuffle_buckets()`** (`_repin_pinned_order`, same gate, no-op when
   unset), which is the single place that reseeds with `seed + epoch` and reshuffles the
   descriptor list at a different length per batch layout. Every caller is therefore
   covered at once: `create_buckets` (dataset build, including the `make_buckets` path
   from `library/datasets/feature_sidecars.py`) and `BaseDataset.set_current_epoch`
   (epoch advance). An earlier revision hooked only `set_current_epoch`, which left the
   build-time reshuffle uncovered (t39 / V40-F2).

   **Not covered:** (a) validation loaders (they already pass `shuffle=False`); (b) any
   non-training consumer that builds its own loader (bench harnesses are measured
   separately and must opt into the same gate). `library/training/auto_block_swap/probe.py`
   is covered *indirectly*: it bumps the epoch through `DatasetGroup.set_current_epoch`,
   which reaches the same `shuffle_buckets()` hook — its probe runs single-process CUDA,
   so it never needed the cross-world alignment in the first place.

The gate is measurement-only. Unset (the default) every builder reproduces the previous
`DataLoader(..., shuffle=True)` / `RandomSampler` behaviour; the negative-control tests
compare sampler type and index sequence rather than object identity.
