## 0. 结论速览

你这次的口径——**图片压小了，单位时间能传的更多，等于带宽更大**——**成立**，而且是图像压缩唯一没有争议的收益方向。正确写法是：

```
有效吞吐 = 链路带宽 × 1 / (1 - 压缩率)
```

但上一条回复给的 6 篇材料，**能用在这个口径上的只有 2 篇（第 1、3 条）**；其中 2 个 arXiv 编号完全指错论文，1 篇查无此文，1 篇指标报错。逐条判定：

| # | 你的断言 | 判定 | 一句话依据 |

## 1. 逐条核验

### 1.1 Lepton（Dropbox / Microsoft）—— 主张成立，编号必须改

**[论文]** 原文身份：

- 标题：*The Design, Implementation, and Deployment of a System to Transparently Compress Hundreds of Petabytes of Image Files for a File-Storage Service*
- 编号：**`arXiv:1704.06192`**（2017-03-26），USENIX NSDI 2017
- 作者：Daniel Reiter Horn, Ken Elkabany, Chris Lesniewski-Laas, Keith Winstein
- 摘要原句（quote）：*"Lepton has been released as open-source software and has been deployed for a year on the Dropbox file-storage backend. As of February 2017, it had compressed more than 203 PiB of user JPEG files, saving more than 46 PiB."*
- 压缩率原句（quote）：*"losslessly compresses JPEG images to 77% of their original size on average"*（即省 23%，官方 README 口径为 "average of 22%"）

**[仓库]** / **[实测]** 生态现状：

- `dropbox/lepton`：4988 stars，**2024-03 已归档**。README 顶部弃用声明明确说不再修 bug 与漏洞（点名 issue #158 报出的漏洞），并建议改用 Microsoft Rust 版、Brotli、WebP 或 JPEG XL。
- `microsoft/lepton_jpeg_rust`：Apache-2.0，最近 push 2026-10-27，PyPI 包 `lepton_jpeg_python` 存在且本文实测可用（版本 0.5.8）。你给的 "pip install lepton_jpeg_python 在训练脚本里边读边用" **成立**。
- 本文实测（12 图 / 73.9 MB，`max_partitions=8`，`PerCpu` 线程池）：**73.9 → 59.6 MB，省 19.39%，位精确还原 12/12 全部通过**，平均编码 0.40 s/图、解码 0.29 s/图。

**判定**：主张成立，但两点要改口径——

1. 编号写成 `arXiv:1703.08865` 会指到别的论文，正确是 `1704.06192`。
2. 它是**位精确可逆**方案，所以天花板就是 ~20%，不存在"硬砍 22% 以上"的空间；且 Lepton 只能被 Lepton 解，浏览器/训练管线不支持，属于"自建管道内部格式"。

### 1.2 LatentStore —— 论文真实，但会议录用是编的

**[论文]** 原文身份：

- `arXiv:2605.19385` v3（2026-05-19），*LatentStore: An Efficient Latent-First Storage System for AI-Generated Images*
- 作者：Zirui Wang, Yunjia Zheng, Tingfeng Lan, Zhaoyuan Su, Haoran Ni, Juncheng Yang, Yue Cheng
- 摘要原句（quote）：*"LatentStore reduces persistent storage by 78.7% with competitive or even lower mean and tail latency over a pure image-based storage."*
- 150 PB 确有原文（quote）：*"storing 100 billion losslessly compressed PNGs requires roughly 150 PB"*；35 个月 / 20 亿请求的 trace 来自 **Civitai**（生成内容平台）。

**判定**：

- "USENIX 2026 存储与系统顶会录用" → **全文检索无 `USENIX` / `NSDI` / `OSDI` / `FAST` 任何字样**，只有 arXiv。这条录用声明**不可引用**。
- 它不是"重打包压缩工具"，是一个**存储系统**：热图保留解码像素做快速命中、冷图存 `compressed latents`、读写路径按需 GPU 重建。78.7% 是它的 DRR 指标（相对纯 PNG 存储），不是"任何数据集都能砍 78.7%"。
- 适用范围极窄：**只对"由已知模型生成的图"成立**，且重建需要当时的 VAE/模型权重。普通照片、网络抓图、二次压缩过的图不适用。你的 q98 原图集不属于此类。

### 1.3 JPEG XL / Chrome 155 —— 一半成立

**[实测]** 版本落地情况（本文交叉验证两处独立源）：

- `chromestatus` feature *"JPEG XL decoding support (image/jxl) in blink"*：`desktop shipped = 155`，摘要写明用纯 Rust 的 `jxl-rs` 解码器，记录更新于 2026-08-31。
- `caniuse` 的 `jpegxl` 数据：Chrome 152–154 为 `n`，**155 起为 `y`**。
- `chromiumdash`：`155.0.8059.84` 已是 Stable；156 为当前 Stable。

→ **"Chrome 155 起支持 JPEG XL" 成立**，这条你抓对了。

**[论文]** 无损重压缩比例：JXL 官方论文（`arXiv:2506.05987`，Sneyers / Alakuijala 等 12 人）原文 *"recompress existing JPEG images, reducing file sizes — and thus transmission and storage costs — by about 20%"*；本文实测 **20.76%**，两者一致。

**判定：以下两点必须改**

1. **"effort=7~9 视觉无损省 55~65%" 不成立**（至少不能当通用结论引用）。实测显示这个数字强依赖原图码率：你的 pixiv 系列是 **q≈98** 的极高码率 JPEG（6~10 MP 却存到 5~11 MB/张），逐像素都能再榨——实测 `-d 1` 省 **77~81%**，`-d 0.5` 省 **64%**，`-d 0.3` 省 **52%**。也就是说 55~65% 既不是上限也不是下限，**唯一可靠做法是在自己数据集上实测**。
2. 你引的"2026 年 10 月 11 日 Chrome 155 实测：21% off existing JPEGs"这篇文章 **DDG / Bing 均 0 命中，我无法证实存在**。能证的只有"Chrome 155 已支持 JXL"和"~20% 与官方口径一致"两件事。**不要把它当第三方实测引用**，要引就引 JXL 论文原文。

## 2. 本机实测：你的 JPEG 到底能压多少

全部数据是本文现跑，可复算（命令见 §9）。**样本：`image_dataset/style_8_4`，57 张 JPEG，295 MB，平均 5.18 MB/张，分辨率 6~10 MP。**

**[实测]** 先定基线——你的原图是什么码率：

| 系列 | 分辨率 | 体积 | IJG 量化表估算质量 |
| --- | --- | --- | --- |
| pixiv_壱珂_* | 2000×4000 ~ 2508×4093 | 4.7~11.1 MB | **q≈98** |
| twitter_ichika087_* | 1825×2580 ~ 2480×3508 | 0.7~3.1 MB | **q≈85** |

这一点决定了后面所有数字：**q98 的原图离"视觉无损"还很远，可压空间比文献里 q90~95 的图大得多**，所以任何"通用压缩率"表格在你这里都会失真。

### 2.1 无损（位精确可逆）

| 方案 | 样本 | 压缩前 → 后 | 省 | 等效带宽 | 编码 | 解码 | 位精确 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| JXL 无损 JPEG 重压缩（`-d 0 -e 8`） | 12 图 / 73.9 MB | 73.9 → 58.6 MB | **20.76%** | **1.26×** | ~2.5 s/图 | ~0.31 s/图 | ✓ 12/12 |
| Lepton（Rust 0.5.8，`max_partitions=8`） | 12 图 / 73.9 MB | 73.9 → 59.6 MB | **19.39%** | **1.24×** | 0.40 s/图 | 0.29 s/图 | ✓ 12/12 |

→ **无损路线天花板 ≈ 1.25×**。这是物理上限，不是实现问题：JPEG 熵编码已是既成事实，重排 Huffman 只能收回这么多。要更大幅度必须动量化（= 有损）或动分辨率（见 §2.3）。

### 2.2 有损 JXL（全分辨率不动，只改编码质量）

| 档位 | 样本 | 压缩前 → 后 | 省 | 等效带宽 | 编码 | 解码 |
| --- | --- | --- | --- | --- | --- | --- |
| `-d 0.3` | 8 图 / 37.8 MB | 37.8 → 18.1 MB | 52.27% | 2.10× | 1.2 s/图 | 0.10 s/图 |
| `-d 0.5` | 8 图 / 37.8 MB | 37.8 → 13.5 MB | 64.22% | 2.79× | 1.2 s/图 | 0.10 s/图 |
| `-d 1.0` | 8 图 / 37.8 MB | 37.8 → 8.7 MB | 77.13% | 4.37× | 1.8 s/图 | 0.10 s/图 |
| `-d 1.0` | 12 图 / 73.9 MB | 73.9 → 14.0 MB | **81.06%** | **5.28×** | 1.9 s/图 | 0.10 s/图 |

`-d 1.0` 的画质代理：PSNR 41.83 dB 平均，最低 35.98 dB（动漫线条属于 PSNR 不友好内容）。**`-d 1.0` 只是 libjxl 口径的 1 JND 阈值，不等于"训练无损"**；对扩散模型训练这种对高频纹理敏感的用途，建议从 `-d 0.5` 起试，并对缓存 latent 做一次 A/B。

### 2.3 最大的杠杆：分辨率，而不是编码器

**[实测]** 你的原图是 6~10 MP，而训练实际消费的是 `CONSTANT_TOKEN_BUCKETS` 级分辨率（约 1~1.3 MP 量级）。把原图降到训练真实使用尺寸后再编码：

| 处理 | 样本 | 压缩前 → 后 | 省 | 等效带宽 |
| --- | --- | --- | --- | --- |
| 缩到最长边 1344 px + JXL `-d 0.5` | 10 图 / 54.7 MB | 54.7 → 4.2 MB | 92.3% | **13.0×** |
| 缩到最长边 1344 px + JXL `-d 1.0` | 10 图 / 54.7 MB | 54.7 → 2.7 MB | 95.1% | **20.6×** |
| 缩到最长边 1024 px + JXL `-d 0.5` | 10 图 / 54.7 MB | 54.7 → 2.7 MB | 95.1% | **20.3×** |
| 缩到最长边 1024 px + JXL `-d 1.0` | 10 图 / 54.7 MB | 54.7 → 1.7 MB | 96.9% | **31.8×** |
| 缩到最长边 1344 px + JPEG q95 | 10 图 / 54.7 MB | 54.7 → 5.8 MB | 89.4% | 9.4× |
| 缩到最长边 1024 px + JPEG q95 | 10 图 / 54.7 MB | 54.7 → 3.8 MB | 93.1% | 14.5× |

**读法**：即使完全不换格式、继续用 JPEG，只做"降到训练分辨率 + q95"，也能拿到 **9~14×**；换成 JXL 再叠 **1.4~2×**。也就是说 **编码器是二阶项，分辨率是一阶项**。

**[推论]** 这是有损的、不可逆的决策，必须先确认：你的训练桶上限是多少、是否还要留出放大/裁剪的余量、原始 q98 原图是否要另存归档。本文不建议直接执行，只给出量级。

### 2.4 对照基准：传统 JPEG 重压缩（q95 / q92）

这是最该先算的对照组——**你的管线本来就认 `.jpg`，零代码改动，编码 CPU 几乎免费**。

**[实测]** 10 图 / 54.7 MB，全分辨率不缩放。质量指标为 **RGB 三通道平均**的 PSNR 与 SSIM（高斯窗 σ=1.5），编码用 PIL/libjpeg-turbo：

| 方案 | 总 MB | 省 | 等效带宽 | PSNR | SSIM | 编码耗时 |
| --- | --- | --- | --- | --- | --- | --- |
| JXL 无损重压缩 | 43.7 | 20.1% | 1.25× | 51.90 | 0.9962 | 2.10 s |
| JPEG **q98** 4:4:4 | 37.4 | 31.5% | **1.46×** | 49.18 | 0.9933 | **0.077 s** |
| JXL `-d 0.5` | 17.6 | 67.7% | **3.10×** | 45.75 | 0.9884 | 1.19 s |
| JPEG **q95** 4:4:4 | 24.8 | 54.6% | **2.20×** | 45.27 | 0.9864 | **0.067 s** |
| JPEG q92 4:4:4 | 18.8 | 65.6% | **2.91×** | 43.32 | 0.9813 | 0.063 s |
| JXL `-d 1.0` | 10.9 | 80.2% | **5.04×** | 42.90 | 0.9822 | 1.78 s |
| JPEG q95 4:2:0 | 18.7 | 65.9% | 2.93× | 41.85 | 0.9766 | 0.043 s |
| JPEG q92 4:2:0 | 14.2 | 74.0% | 3.84× | 40.65 | 0.9712 | 0.040 s |
| JPEG q90 4:2:0 | 12.9 | 76.4% | 4.24× | 40.04 | 0.9683 | 0.039 s |

**三条硬结论：**

1. **不想改代码，JPEG 重压缩就够用**。q95 4:4:4 给 2.20×、q92 4:4:4 给 2.91×，编码只要 0.06~0.08 s/图——比 `cjxl -e 7`（1.2~2.1 s）快 **26~28 倍**。整库转码成本从"38 小时/TB"降到"1.5 小时/TB"量级。
2. **等画质交叉对比，JXL 才显出价值**（同质量下更小）：
   - 约 45.3~45.8 dB / SSIM ≈ 0.986~0.988 档：JPEG q95 4:4:4 = 24.8 MB，JXL `-d 0.5` = 17.6 MB → **JXL 再省 29%**
   - 约 43 dB / SSIM ≈ 0.981~0.982 档：JPEG q92 4:4:4 = 18.8 MB，JXL `-d 1.0` = 10.9 MB → **JXL 再省 42%**
   也就是说 JXL 的增量收益是 1.3~1.7×，**不是**上一轮里 5.3× vs 1.26× 那种量级差（那个对比是"JXL 有损 vs Lepton 无损"，不同画质档，不能这么比）。
3. **4:2:0 是隐性降质**。同为 q95，4:2:0 只有 41.85 dB / SSIM 0.9766，比 4:4:4 的 45.27 dB / 0.9864 低 3.4 dB，但体积只小 25%。你的 pixiv 原图本来就是 **4:4:4**，转 4:2:0 是纯损失，插画/线稿的高饱和色边会糊。

**[实测] 补充：不能一刀切全库重编码。** 两个子集的原图码率差一个世代：

| 子集 | 原图 | q95 4:4:4 | q92 4:4:4 | q90 4:2:0 |
| --- | --- | --- | --- | --- |
| pixiv（q100 / 4:4:4，5.9 MB/张） | 47.0 MB | 省 57.3%（**2.34×**） | 省 67.8%（3.11×） | 省 78.5%（4.65×） |
| twitter（q85 / 4:2:0，1.4 MB/张） | 11.6 MB | **涨 3.6%（0.97×）** | 省 17.3%（1.21×） | 省 40.5%（1.68×） |

→ 对已经压过的低码率图，重编码到 q95 **反而变大**，还叠加一次世代损失。**必须逐文件判断"重编码后是否更小"，不要按目录/统一参数批处理。**

**[实测] 一个容易误读的点**：JXL 无损重压缩的 PSNR 只有 51.90 dB 而不是无穷大，是因为 `djxl` 与 libjpeg 的 IDCT 实现不同、像素有 ±1 LSB 差异；**文件本身是位精确可逆的**（§2.1 已用 `cmp` 逐字节验证 12/12）。同理，"JPEG q98 4:4:4 比 JXL 无损更小（1.46× vs 1.25×）"不代表 JPEG 更好——q98 已经是有损（49.18 dB），两者不在同一档。

#### 分档结论

1. **体积档位不改变画质排序，只改变"值不值得转"**：5–10 MB 与 10–15 MB 两个大图档的压缩率基本一致（q95 4:4:4 约 56–58%、JXL `-d 1.0` 约 80–82%），说明**原图码率（q100/4:4:4）才是决定压缩率的变量，体积只是它的代理指标**。
2. **1–5 MB 档是"陷阱档"**：里面是已经压过一轮的图，任何"提高质量参数的重编码"都会变大。这一档只能往更低参数走，或者上 JXL 有损。
3. **等画质交叉（以 5–10 MB 档为例）**：JPEG q95 4:4:4（43.40 dB / SSIM 0.9837 / ΔE76 0.93，15.7 MB）vs JXL `-d 0.5`（44.15 dB / 0.9864 / 0.92，11.5 MB）→ **JXL 三项指标全更好且再省 27%**；JPEG q92 4:4:4（41.12 / 0.9764 / 1.15，11.9 MB）vs JXL `-d 1.0`（41.14 / 0.9787 / 1.24，7.2 MB）→ **再省 39%**（ΔE 略差 0.09，仍在肉眼难辨区间）。
4. **色度损失在 R/B 通道集中体现**：4:2:0 档的 R/B 比 G 低 5~7 dB，ΔE95 从 3~4 跳到 6~8。选 4:4:4 不是洁癖，是插画类内容的实际画质边界。

## 3. 等效带宽换算

```
传输时间 T = 原始体积 × (1 - 压缩率) / 链路带宽
有效吞吐倍数 = 1 / (1 - 压缩率)
```

**[实测]** 按你之前的 8 TB 口径折算（8 TB = 8×10⁶ MB）。除最后两行（降分辨率，10 图样本）外，倍数均取自 §2.4 的同一 10 图 / 54.7 MB 样本，保证可比：

| 方案 | 倍数 | 需要传的量 | @100 Mbps（12.5 MB/s） | @1 Gbps（125 MB/s） |
| --- | --- | --- | --- | --- |
| 不压缩 | 1.00× | 8.0 TB | 7.4 天 | 17.8 h |
| JXL 无损重压缩 | 1.25× | 6.4 TB | 5.9 天 | 14.2 h |
| **JPEG q95 4:4:4** | 2.20× | 3.6 TB | 3.4 天 | 8.1 h |
| **JPEG q92 4:4:4** | 2.91× | 2.7 TB | 2.6 天 | 6.1 h |
| JXL `-d 0.5`（全分辨率） | 3.10× | 2.6 TB | 2.4 天 | 5.7 h |
| JXL `-d 1.0`（全分辨率） | 5.04× | 1.6 TB | 1.5 天 | 3.5 h |
| 1344 px + JXL `-d 0.5` | 13.0× | 0.62 TB | 13.7 h | 1.4 h |
| 1024 px + JXL `-d 1.0` | 31.8× | 0.25 TB | 5.6 h | 0.6 h |

**关键认知**：带宽瓶颈下，"无损压缩"给你的边际收益（+26%）可能还不如换一条更好的网络链路；而"降分辨率"给你的 13~20× 是换网络也很难买到的量级。**先算清楚瓶颈是链路还是 CPU。**

## 4. 代价账：省下来的带宽要用 CPU 和画质换

### 4.1 一次性转码成本（本机 36 逻辑核，`cjxl v0.12.0`）

**[实测]** 32 图 / 220.1 MB：

| 参数 | 墙钟 | 吞吐 | 源 JPEG 处理速率 | 压缩率 |
| --- | --- | --- | --- | --- |
| `-e 7`，并发 8 | 31.2 s | 1.03 图/s | 7.1 MB/s | 81.1% |
| `-e 7`，并发 16 | 28.6 s | 1.12 图/s | 7.7 MB/s | 81.1% |
| `-e 3`，并发 16 | 9.0 s | 3.55 图/s | 24.4 MB/s | 82.9% |

折算成规模成本：`-e 7` ≈ **38 小时/TB 源图**，`-e 3` ≈ **12 小时/TB 源图**（`-e 3` 的压缩率没有变差，本样本甚至略好，但这是编码器启发式差异，别当规律）。注意 cjxl 单张内部已多线程，**堆并发到 16 之后吞吐不再涨**（1.03 → 1.12 图/s），说明 36 核对 `-e 7` 基本吃满。

**[实测] 作为对照，传统 JPEG 重编码便宜得多**：PIL/libjpeg-turbo 单张 0.06~0.08 s，折算单核约 **3.4 小时/TB**，16 并发约 **13 分钟/TB**——比 `cjxl -e 7` 快 26~28 倍，且 16 并发能真正线性扩展（JPEG 编码器本身不抢核）。

**[推论]** 若同时降分辨率，编码量随像素数下降，转码耗时会明显低于上表（未实测）。

### 4.2 训练期解码成本（每 epoch 都要付）

**[实测]** 单图平均：

| 解码路径 | 耗时 |
| --- | --- |
| PIL 解 JPEG + convert RGB（现状基线） | 0.134 s |
| `djxl` 解 JXL（含写 ppm） | 0.10 s |
| Lepton 解码（Rust） | 0.29 s |

→ **JXL 解码不比 PIL 解 JPEG 慢，Lepton 反而慢一倍多**。这点和直觉相反，值得记住：Lepton 的算术编码解码是纯 CPU 顺序解码，JXL 的解码器有 SIMD 优化。

**[推论]** 上表是 CLI 单进程数据；进 DataLoader 后实际数字取决于 worker 数、`pillow_jxl` 是否启用多线程解码、以及是否命中 VAE latent 缓存。要走这条路必须先做一次 dataloader 吞吐 A/B。

### 4.3 画质成本

- `-d 0`（JXL 无损重压缩 / Lepton）：**位精确，画质零成本**，唯一代价是 +20% 的空间换 1.25× 带宽。
- `-d 0.3 ~ -d 1.0`：有损。PSNR 41.8 dB 平均不代表训练安全，扩散模型对高频细节敏感，必须用 latent/生成质量做 A/B，不能只看 PSNR。
- 降分辨率：**信息不可逆丢失**，是三者中唯一真正需要你决策的一项。

## 6. 推荐方案（按你的实际目标排序）

### 起点：先问一句，为什么不用传统 JPEG 重压缩？

如果你的目标是"少传点字节"而不是"用最新格式"，**按性价比排序，JPEG 重压缩应该排第一**：

| 方案 | 等效带宽 | 画质（SSIM） | 代码改动 | 编码成本 |
| --- | --- | --- | --- | --- |
| JPEG q95 4:4:4 | 2.20× | 0.9864 | **0** | 0.07 s/图 |
| JPEG q92 4:4:4 | 2.91× | 0.9813 | **0** | 0.06 s/图 |
| JXL `-d 0.5` | 3.10× | 0.9884 | 需补代码 | 1.19 s/图 |
| JXL `-d 1.0` | 5.04× | 0.9822 | 需补代码 | 1.78 s/图 |

要点：

- **q95 4:4:4 是"零风险起点"**：管线零改动、编码近乎免费、SSIM 0.9864。绝大多数"带宽/硬盘不够"的场景，2.2× 就已经解决了。
- 想再省一档就上 **q92 4:4:4**（2.91×，SSIM 0.9813）；**不要用 4:2:0**，同体积下画质掉 3.4 dB，插画尤其明显。
- JXL 的边际收益是"同画质再省 29%~42%"，值不值得取决于你补 `jpeg_xl_util.py` + 装 `pillow-jxl` 的成本，以及能接受 26 倍的编码时间。**它不是必需品。**
- **必须逐文件判断**：先算"重编码后是否更小"再写回。你库里 q85/4:2:0 的那批图重编码到 q95 会**变大 3.6%**。

### A. 如果目标是"同样的盘/同样的网，装更多、传更快"，且不能接受任何画质变化

1. 选 **JXL 无损重压缩**，不要选 Lepton。理由：压缩率同级（20.76% vs 19.39%），但 JXL 是 ISO/IEC 18181 标准、Chrome 155+ 原生可解、解码更快、`dropbox/lepton` 已归档且有未修漏洞。
2. 收益预期：**1.26×**。8 TB → 6.3 TB。
3. 前置：补 `jpeg_xl_util.py` + 装 `pillow-jxl`。

### B. 如果目标是"把带宽真正放大一个量级"，且能接受视觉无损

按收益/风险排序，逐级验证：

1. **先降分辨率到训练真实使用尺寸**（13~20×，一阶项，需你拍板是否留原图归档）。
2. **再叠 JXL `-d 0.5`**（在已降分辨率基础上再 1.4~2×）。
3. 上线前必做：latent 缓存 A/B（同一 subset，同 step 数，比 loss 曲线与出图），不要只看 PSNR。

### C. 如果瓶颈其实是"训练数据加载慢"而不是"网络慢"

那就不是压缩问题，而是 latent 缓存问题：`{stem}_{WxH}_anima.npz` 这类 sidecar 缓存命中后，训练期根本不读原图。**先去确认你的瓶颈到底在链路、磁盘 IO 还是 dataloader**，否则压缩省下的字节对训练没有帮助。

### D. 关于显存那三条（本次目标之外）

- GACT（`arXiv:2206.11357`）**真实可用**，但引用时把数字改对：8.1× 激活显存、batch 4.2~24.7×、吞吐 75%~136%、ResNet-50 精度 −0.33%。
- INSTANT **不存在，删掉**。
- dreaMLearning（`arXiv:2506.22190`）只在小图上验证过，不要引到高分辨率数据集上。

## 7. 未验证项与风险

- **未验证**：JXL 有损档位对扩散模型训练质量的影响（本文只给了 PSNR / SSIM 代理指标，未做训练 A/B）。**JPEG q95/q92 出同样只测了代理指标**——注意这两个指标对"线条锐度、色边、渐变带状"的判定与人眼/生成模型并不一致，插画类内容尤其需要肉眼比对局部 100% 裁切。
- **未验证**：降分辨率后训练质量的影响（本文只测了字节数，未训练）。
- **未验证**：`pillow_jxl` 进 DataLoader 后的真实解码吞吐（本文用 `djxl` CLI 代理）。
- **未验证**：LatentStore 的 78.7% 在你的场景是否可达（它的前提是 AI 生成图 + GPU 重建路径，你的数据不满足前提）。
- **风险**：本文样本只有 12 张（压缩率）/ 32 张（吞吐），来自单一人设目录 `style_8_4`，其中 pixiv 系列 q≈98、twitter 系列 q≈85，两类混合后平均值会掩盖差异。**正式决策前请在你完整数据集上重跑 §9 的命令。**
- **风险**：`-e 3` 在本样本上压缩率反而略好于 `-e 7`，属于编码器启发式差异，不要当成"低 effort 更省空间"的规律。

## 8. 复现命令

```bash
# 0) 无损 JPEG 重压缩（位精确）+ 往返校验，实测 20.76%
cjxl input.jpg out.jxl -d 0 -e 8
djxl out.jxl back.jpg
cmp back.jpg input.jpg && echo BITEXACT

# 1) 有损档位扫描，实测 -d 0.3/0.5/1.0 = 52.3%/64.2%/77.1%（8 图）~ 81.1%（12 图）
cjxl input.jpg out.jxl -d 1 -e 7 --lossless_jpeg=0   # 必须显式关掉 lossless_jpeg，否则报错退出
djxl out.jxl out.ppm                                  # 解到 ppm 才是公平的解码耗时

# 2) Lepton 对照（需 pip install lepton_jpeg_python）
python3 -c "
import lepton_jpeg_python as L
cfg={'max_jpeg_width':20000,'max_jpeg_height':20000,'progressive':True,
     'reject_dqts_with_zeros':False,'max_partitions':8,'max_jpeg_file_size':256*1024*1024}
b=open('input.jpg','rb').read(); c=L.compress_bytes(b,cfg)
assert L.decompress_bytes(c,cfg)==b; print(f'{len(b)} -> {len(c)}')
"

# 3) 降分辨率 + 编码（一阶项）
python3 -c "
from PIL import Image; import subprocess
im=Image.open('input.jpg').convert('RGB'); im.thumbnail((1344,1344), Image.LANCZOS)
im.save('/tmp/t.png'); subprocess.run(['cjxl','/tmp/t.png','out.jxl','-d','0.5','-e','7'])
"

# 3b) 传统 JPEG 重压缩对照（4:4:4 必须显式指定 subsampling=0，否则默认是 4:2:0）
python3 -c "
from PIL import Image; import os
im=Image.open('input.jpg'); im.load()
for q in (98,95,92):
    im.convert('RGB').save('/tmp/q.jpg', format='JPEG', quality=q, subsampling=0)
    print(q, os.path.getsize('/tmp/q.jpg'))
"

# 4) 源图质量估算（判断可压空间的前提）
python3 -c "
from PIL import Image; import numpy as np
q=Image.open('input.jpg').quantization; t=q.get(0) or list(q.values())[0]
s=sum(t[:8])/sum([16,11,10,16,24,40,51,61]); print('q~', round(100-50*np.log2(s) if s>1 else 100-50*s))
"
```

环境口径：`cjxl v0.12.0 a7a9c787 [_AVX2_,SSE4,SSE2]`，36 逻辑核，`lepton_jpeg_python 0.5.8`，Pillow 12.3.0。产出全部写入 `/tmp`，未改动 `image_dataset/` 与 `post_image_dataset/`。
